## 一、这个项目现在是什么

一个本机离线的 CTF 知识库：**1567 篇文档 + 中文模糊检索 + 本地小模型问答 + React 前端**。

它的历史使命已经完成了一轮：
从「一个空的 md 目录」做到了「能一键启动、能检索、能出思路」的可用工具。

现在站在一个岔路口：**功能上它已经够用，但结构上它还没成形。**

---

## 二、三个判断

### 判断 1：知识库的「量」已经够了，问题在「质」

| | 数量 |
|---|---|
| 手写条目 | 241 |
| 外部导入 | 266 + 1060 |
| **合计** | **1567** |

再看这个数字：**图谱只有 26 条边，覆盖率 7%**。

也就是说，1567 篇文档之间**几乎没有连起来**。检索只能靠词面/语义相似，
而真实 CTF 里最有价值的是「这题和那题是同一类」，这正是图谱该干的事，
现在基本是空的。

> **方向 1：从「堆文档」转向「织网络」。**
> 下一步加知识不该是「再加 1000 篇」，而是「让已有的 241 篇手写条目互相连通」。

### 判断 2：评测体系缺失，是所有改进的瓶颈

现状：

```
pytest        82 passed   ← 全是引擎/工具层单元测试
server.py     0 测试      ← 整个 Web 服务无覆盖
webapp        0 测试      ← 前端零测试
检索质量      无基准      ← 改了排序不知道是变好还是变坏
```

之前做过两轮「模拟 CTF 解题」测试（见 `work/judge/ROUND2_REPORT.md`），
结论是 **2/5 解出，17 次检索只有 2 次真正有用（12%）**。
但那个测试**环境不完整、不可复现**：Docker 容器要手动起，题目数据每次手搓。

**没有可复现的评测，任何「优化」都是盲改。**

> **方向 2：先建评测，再谈优化。**
> 一小时内能跑完、结果可比的评测集，比任何单点功能都重要。

### 判断 3：模型这条路已经到顶，不该再投入

实测数据：

```
Qwen3-4B       24 tok/s（结构化判断），883 段/105 秒一次回答
Qwen2.5-7B     13-19 tok/s，且把正确方法判成「不适用」
AirLLM 方案    0.006–0.026 tok/s（每 token 读一遍完整模型）
显存           4GB，7B Q4 已是极限
```

**结论：本机跑不了更大的模型，而 4B 已经能在「判断候选是否匹配」这类
结构化任务上用了。** 继续投入模型侧（换框架、换量化、搞 AirLLM）
收益接近零。

> **方向 3：停止在模型侧投入，把算力用在「工具出事实」上。**
> 项目已有的架构原则是对的：**工具产生事实，模型只做判断/排序**。
> 沿着这条路走，而不是指望模型变聪明。

## 三、建议的主线：让知识库「会推理」，而不是「会检索」

现在的链路：

```
查询 → 检索 → 列出文档 → 模型选一条回答
```

目标链路：

```
查询/附件 → 侦察 → 检索 → 图谱关联 → 结构化证据 → 模型判断 → 可执行步骤
```

差别在于：**中间多了「图谱关联」和「结构化证据」**。

具体到写什么，按我的优先级：

### P0 —— 打地基（不做后面都是空谈）

| # | 事项 | 理由 | 预估 |
|---|---|---|---|
| 1 | `git init` + 首次提交 | 现在无版本控制，任何改动不可回滚 | 10 分钟 |
| 2 | 修白屏（`setImmediate`）+ SSE 错误回显 | 影响可用性和可观测性 | 20 分钟 |
| 3 | `server.py` 加冒烟测试 | 375 行服务零覆盖，改坏了不知道 | 1 小时 |
| 4 | 建 20 条评测集 | 检索/问答质量的可比基准 | 半天 |

**第 4 条是重点。** 评测集建议这样建：

```yaml
# tests/eval/queries.yaml
- q: "题目给了同一个 n，e1=3 e2=65537，两组密文"
  expect_top1: crypto/rsa-common-modulus-attack.md
  expect_in_top5: [crypto/rsa-common-modulus-attack.md, crypto/rsa-wiener-attack.md]
  kind: 手写条目（必须命中）
- q: "Solidity calldata tuple head overflow"
  expect_top1: _des/cards/...(那篇 0CTF 卡)
  kind: 导入条目（宽松，进前 5 即可）
```

跑法：`kb bench-retrieval`，输出 **top1 命中率 / top5 命中率 / MRR**。
以后每次改排序，先跑这个。

### P1 —— 让图谱真正起作用

这是当前最大的结构缺口，也是最能体现「知识库」而不是「文档集合」的地方。

| # | 事项 | 做法 |
|---|---|---|
| 5 | 给 241 篇手写条目补关系 | 先补 50 篇高频条目的 `requires` / `differs_from` |
| 6 | 实现「反向索引」式关系建议 | 从已有 26 条边出发，找出「很像但没连」的文档对，人工确认后加边 |
| 7 | 检索时按关系加权 | 现在图谱结果只排尾部；应让 `requires`/`illustrated_by` 真正提升排名 |

**第 6 条是杠杆点**：与其让模型去猜关系，不如让工具**找出候选对**，
人只做「是/否」。这个模式在 `hint` 里已经验证过有效
（工具出事实，模型只判断）。

### P1 —— 评测驱动的检索优化

| # | 事项 | 做法 |
|---|---|---|
| 8 | 修复排序噪音 | 主题文档 vs WP 卡片需要类型加权（已知问题） |
| 9 | 引入字段加权可调 | 现在列权重是硬编码，应可配置并纳入评测 |
| 10 | 每个改动都跑评测 | 用 P0 建立的基准做回归 |

### P2 —— 让「没思路」这件事真正被解决

`kb hint` 是项目里最有特色的功能（侦察附件 → 工具出事实 → 模型推方向），
但**只在命令行可用，前端没有入口**。

| # | 事项 | 做法 |
|---|---|---|
| 11 | 前端加「上传附件」入口 | 拖入文件 → 调 `/api/hint` → 显示侦察结果 + 方向 |
| 12 | 侦察结果结构化展示 | 现在只输出文本，应该展示：文件类型、雕刻命中、解码结果 |

这一条把 CLI 的能力开放给界面，收益直接。

### P2 —— 内容补齐（其次）

| 15 | 继续加知识 | 但只在上面都做完了再加 |

## 四、不建议做的事（明确排除）

写下来免得后面反复讨论：

| ❌ 不做 | 原因 |
|---|---|
| 换更大的模型 / AirLLM | 实测 0.006–0.026 tok/s，不可用 |
| 换推理框架（vLLM 等） | 4GB 显存，瓶颈不是框架 |
| 加 RAG 微调 | 数据量不够，且当前瓶颈在检索不在生成 |
| 做多智能体 / Agent 框架 | 当前单次问答已 105 秒，多步会更慢 |
| 继续无脑导语料 | 1567 篇已经够多，覆盖率才是问题 |
| 做在线/云服务 | 项目定位是本机离线 |

## 五、判断标准：什么算「这个项目变好了」

给可衡量的指标，否则容易陷入「加功能」的自我感动：

| 指标 | 现在 | 3 个月内目标 |
|---|---|---|
| 评测集 top1 命中率 | 未测 | ≥ 70% |
| 评测集 top5 命中率 | 未测 | ≥ 90% |
| 图谱边数 | 26 | ≥ 150 |
| 手写条目有关系的比例 | 7% | ≥ 60% |
| `server.py` 测试覆盖 | 0 | 核心端点全覆盖 |
| 前端可用的核心路径 | 有白屏风险 | 无阻塞缺陷 |
| 一次问答耗时 | 105 秒 | ≤ 60 秒（减上下文/降 top_k） |

## 六、如果只做三件事

时间有限的话，按这个顺序：

1. **`git init` + 修白屏** —— 30 分钟，把地基问题清掉
2. **建 20 条评测集** —— 半天，之后所有优化都有尺子
3. **给 50 篇高频手写条目补关系** —— 2-3 天，让图谱从「摆设」变「可用」

第 3 件事做完，这个项目才真正从「文档集合」变成「知识库」。

## 七、一句话

> 项目已经过了「从无到有」的阶段，接下来该走「从散到连」——
> 用评测驱动，把手写条目织成网络，让检索能沿着关系往下走。
> 模型侧不用再投入，工具侧还有很多事没做。
