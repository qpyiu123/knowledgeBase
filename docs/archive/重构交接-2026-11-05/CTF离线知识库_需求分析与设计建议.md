# CTF 离线知识库：需求分析与设计建议

日期：2026 年 10 月 25 日  
用途：重构讨论稿，用于明确需求、比较方案和安排概念验证。

## 摘要

这个项目的目标，是在离线 CTF 解题过程中，帮助使用者查清工具与语言行为、理解相关原理、找到可参考的操作方法，并根据当前证据选择下一步。

历史题解、系统教程和 API 文档提供的是三种不同的知识：题解记录一次具体问题如何被解决，教程解释一类问题的方法与条件，API 文档描述一个接口在特定版本中的行为。它们应当保留各自结构，再通过方法、条件、代码和案例建立关联。

重构的关键，是从“收集文章并回答问题”转向“围绕当前任务组织可用知识”。对 WP，需要重建作者公开记录中的条件、操作与结果；对教程，需要提炼可复用的方法；对 API，需要保留精确的名称、参数、类型、版本和示例。检索与模型再根据使用者的需求选择这些内容，而非把全部资料压进同一种卡片。

建议采用的总体方向是：

> **分类型理解资料，按任务组织检索，用原文支撑解释，用单题记录维护解题进度。**

## 一、项目定位与需求边界

### 1.1 要解决的核心问题

CTF 覆盖的领域、工具和语言很多。做题者经常知道自己卡在哪里，却想不起对应术语、适用方法或具体工具用法。项目应当缩短从“发现问题”到“找到依据并完成下一项有效检查”的时间。

它需要支持三个连续但可以独立使用的环节：

1. **查清楚**：找到准确的文档、原理、代码和案例。
2. **想明白**：解释资料为什么相关，识别成立条件，比较可行路线。
3. **记下来**：保存当前证据、假设、尝试与结果，减少重复探索。

使用者查一个函数时，可以直接获得答案；在复杂题目中，也可以把这些查询组织成完整的解题记录。

### 1.2 已经明确的需求

| 需求 | 对设计的影响 |
| --- | --- |
| 比赛时离线使用 | 推理、检索、文档解析、资源加载和资料阅读都应有本地路径 |
| 主要在笔电上运行 | 快速搜索与生成模型分开，控制常驻内存与查询计算量 |
| 资料包含 WP、教程与 API 手册 | 分别解析和提炼，保留不同资料的结构 |
| 支持关键词与模糊描述 | 精确符号、全文与语义检索配合使用 |
| 本地 4B／9B 模型可选 | 将任务拆成小模型能处理的阅读、解释和候选比较 |
| 需要代码示例和操作方法 | 将完整代码及其条件作为可直接查看的内容 |
| 需要下一步路线建议 | 结合当前证据、目标、条件缺口与历史尝试检索 |
| 需要步骤可视化记录 | 保存实际尝试，区分事实、假设与模型建议 |
| 后续持续加入新资料 | 支持去重、版本、增量更新和来源追踪 |

### 1.3 本阶段交付什么

本阶段先确定资料如何表达、查询如何分流、结果如何判断，以及怎样验证设计。数据库产品、前端框架、向量索引和具体模型作为后续选型。

自动执行题目脚本、完全自主解题和训练专用模型，可以作为后续独立课题。当前流程以使用者选择和执行操作为主，工作台提供资料、解释、候选与记录。

## 二、从做题需求出发，而非从文档目录出发

同一句查询可能对应不同任务。“AES 解密”可能是在找普通解密示例，也可能是在分析没有密钥的题目。进入复杂流程前，应该先识别使用者想获得什么。

### 2.1 六类主要使用场景

| 场景 | 使用者的问题 | 主要资料 | 理想输出 |
| --- | --- | --- | --- |
| 查行为与用法 | 这个函数如何调用，参数表示什么？ | API 文档、工具手册 | 签名、输入输出、版本、示例和容易误用的地方 |
| 理解原理 | 这个现象为什么发生，这种方法为什么有效？ | 教程、原理说明 | 机制、成立条件、示意案例与相关概念 |
| 找操作示例 | 有没有能参考的脚本或命令？ | 示例、代码、WP | 完整片段、依赖、参数含义、适用环境与来源 |
| 找相似案例 | 有没有题目出现过类似特征？ | WP、案例记录 | 相似点、差异、相关步骤及迁移条件 |
| 排查当前错误 | 为什么执行失败或结果异常？ | 手册、失败记录、案例 | 按成本排序的检查项，以及不同结果如何解释 |
| 选择下一步 | 已经知道这些，还可以怎样推进？ | 方法、案例、当前题目记录 | 少量候选路线、依据、缺失条件和下一项检查 |

任务可以组合。例如“解释这段代码并给一个修改示例”，同时涉及原理、API 和代码；“下一步怎么办”也可能先需要查询工具参数。

### 2.2 查询目的、搜索深度与输出形式分别设置

建议将现在容易混在一起的三个选择拆开：

- **查询目的**：查用法、学原理、找案例、排错、规划路线。
- **搜索深度**：快速、增强、多轮调查。
- **输出形式**：资料列表、解释、代码示例、步骤建议或对比表。

这样，“深入查找＋代码示例”能够同时成立。勾选代码既影响召回，也应影响最终结果展示。

对于含糊的短查询，先给几个明确分组，再让使用者选择。资料可以先出现，澄清问题与模型分析随后进行，避免每次都停下来追问。

### 2.3 当前题目上下文按需参与

查询可以独立使用，也可以结合当前题目。参与分析的信息应当清楚可见：

- 当前目标与已完成的子目标；
- 已确认的观察和对应材料；
- 使用者提出的假设；
- 可使用的输入、接口、文件与工具；
- 环境、版本和资源限制；
- 已尝试操作及结果。

单纯查一个 API 时，通常无需把整道题的历史交给模型。规划下一步时，则应选取与当前问题有关的记录。使用者可以修改这份上下文，避免旧假设持续影响后续查询。

## 三、三类资料分别提供什么知识

### 3.1 API 文档：精确的行为参考

API 文档主要回答“这个接口怎样工作”。建议保留：

- 语言、库、模块、完整符号名和版本；
- 函数签名、参数、类型、返回值与异常；
- 状态变化、副作用和调用顺序；
- 关键边界行为；
- 示例、相关接口和原文位置。

检索以完整符号、模块、错误信息和版本为重要入口。结果应直接展示文档条目与示例，再按需解释其与题目的关系。

API 的正常行为与利用这种行为的解题方法分别保存。查询函数时，先查清行为；需要分析题目时，再关联有明确条件的方法。

### 3.2 教程：可复用的方法与解释

教程主要回答“为什么这样做、什么时候可以这样做”。建议提炼：

- 概念和机制；
- 输入条件与预期目标；
- 方法步骤及依赖；
- 适用范围、限制与反例；
- 演示代码、练习和相关知识。

同一教程可能包含多个方法，也可能比较几种相近方法。保留这些差别，比将全文压成一张标签很多的卡片更有价值。

### 3.3 WP：具体案例中的条件、操作与结果

WP 主要回答“这道题当时怎样被解决”。其中最有价值的内容通常是：

- 初始题目提供了什么；
- 作者发现了什么特征；
- 某个操作用了哪些输入；
- 操作产生了什么中间结果；
- 这些结果怎样支持下一步；
- 最后如何达到题目目标。

WP 往往经过事后整理，可能跳过基础知识、失败尝试、环境准备和关键中间结果。它的叙述顺序也可能服务于讲解，而非实际执行顺序。

因此，WP 的处理重点是重建公开材料中的操作依赖与状态变化，再判断其中哪些方法能够迁移。

### 3.4 按内容片段识别角色

资料类型是处理依据，不必变成三个互相隔离的资料库。一篇 WP 可能包含完整原理教程；一份 API 手册也可能附带多步操作指南。

建议同时记录：

- **来源类型**：题解、教程、手册、个人笔记等；
- **片段角色**：原理、接口、步骤、代码、结果、反例等；
- **技术主题**：算法、语言、工具、平台和题型；
- **质量记录**：引用检查、内容核对、运行验证等。

四者分别表达不同信息。教程身份、官方来源或卡片格式，都不直接决定某个片段是否适合当前问题。

## 四、WP 的“反推”应该如何理解

### 4.1 分成案例重建、方法抽象和当前匹配

从 WP 获得下一步建议，可以拆成三个任务：

1. **案例重建**：还原这道题公开记录中的条件、操作和结果。
2. **方法抽象**：识别可复用部分，保留成立前提。
3. **当前匹配**：比较当前题目与历史案例，提出可验证的迁移方案。

这三个任务应分别保存结果。作者对题目的描述、整理者提炼的方法，以及模型针对当前题目的推测，有各自的来源和作用范围。

### 4.2 一项操作需要哪些信息

建议每个关键步骤包含：

| 内容 | 回答的问题 |
| --- | --- |
| 前置条件 | 做这一步之前，已经具备什么？ |
| 输入 | 用到了哪个文件、参数、字节数据或接口？ |
| 操作 | 执行什么方法、命令或代码？ |
| 输出 | 得到了什么文件、数据或观察？ |
| 判断依据 | 为什么这个结果值得继续追踪？ |
| 后续依赖 | 哪些步骤需要这个结果？ |
| 环境要求 | 工具、库、平台和版本是什么？ |
| 原文依据 | 哪些段落、代码或图片支持上述描述？ |
| 信息缺口 | 哪些内容原文没有交代？ |

字段按材料能提供的信息填写。原文没有记录执行结果时，就保留缺口；可以再提出验证方法，但应明确它是后续建议。

### 4.3 重建操作依赖，而非复制文章顺序

一个示意案例可能包含：

```text
源码给出加密方式与参数
          ↓
流量中取得编码后的数据 → 解码为字节数据
          ↓                   ↓
          └────── 常规解密 ────┘
                       ↓
                得到某种文件数据
                       ↓
                按文件格式继续处理
```

这张图表达的是输入与结果之间的依赖。它是设计示意，不是一份已经复现的题解。

真实 WP 可能先介绍最终算法，再回头讲参数来源。整理时应连接“谁提供了谁的输入”，而不是把第一个小标题直接记成第一步。

### 4.4 从实例提炼方法时，保留三组信息

- **案例值**：该题中的文件名、参数、偏移和中间结果。
- **方法变量**：迁移到别的题目时需要重新确定的值。
- **成立条件**：数据组织、接口能力、环境与版本等要求。

这样，使用者既能查看原题如何完成，也能看清哪些部分需要替换。某个示例中的固定值，不会被当成所有题目的默认参数。

### 4.5 明确知识来自哪里

建议对重建内容区分：

1. 原文明确陈述；
2. 从代码、输入输出或图片中提取；
3. 整理过程中作出的推断；
4. 人工补充的解释；
5. 后续复现得到的结果。

同一个结论可以同时具有几种依据。引用检查负责确认材料位置，内容核对负责检查推断，运行测试负责验证某个具体环境下的行为。

WP 通常只展示作者选择的一条成功路径。其他可能路径可以作为候选补充，但作者没有记录的尝试历史应保持未知。

## 五、从“找到相似文章”到“给出下一步”

### 5.1 先确定当前目标和可用证据

“下一步”必须相对于当前状态。例如：已经拿到数据但不清楚格式、识别出算法但缺少参数、得到明文但还没识别文件内容，分别需要不同资料。

建议把目标拆到能够验证的程度，例如“确认数据编码”“确定某参数来源”“解释报错”“得到下一段输入”，而非始终以“拿到 flag”作为唯一目标。

### 5.2 从证据向前找，从目标向后查

两种查找方式可以配合：

- **向前匹配**：当前已有的观察，能支持哪些方法或检查？
- **向后查找**：达到这个子目标，需要哪些输入与条件？这些条件又能怎样取得？

WP 提供具体案例中的依赖，教程解释方法为什么成立，API 文档解决某一步如何准确实现。

第一版可以使用结构化字段、文本条件与人工确认，逐步增加规则。先覆盖常见依赖和明确条件，比一开始建立全自动规划器更容易验证。

### 5.3 条件至少区分三种状态

| 状态 | 含义 | 处理方式 |
| --- | --- | --- |
| 已满足 | 当前证据支持 | 可进入可尝试方案 |
| 有冲突 | 当前证据与条件矛盾 | 说明冲突，降低优先级 |
| 未知 | 还缺必要信息 | 给出确认条件的检查项 |

未知条件应当保留为未知。模型的推测也先进入假设列表，经过验证后再更新题目记录。

### 5.4 每条建议应让使用者能采取行动

建议输出：

- 当前要确认或完成的目标；
- 这个方法为什么值得考虑；
- 与历史案例相同和不同的地方；
- 已满足的条件与仍缺的信息；
- 下一项具体检查及所需工具；
- 不同结果分别意味着什么；
- 可参考的代码、手册和来源。

候选排序综合考虑证据支持、条件匹配、操作成本、重复程度，以及检查能否区分多个假设。先给出高、中、低优先级和理由，积累数据后再研究排序模型。

### 5.5 避免用历史答案填补当前题目

相似题中的密钥、算法模式、文件偏移、目标格式和最终结果，都属于历史案例。当前题目要使用这些条件，需要自己的证据。

同样，在评估“解决新题”的能力时，应将测试题自身 WP、转载和近重复材料单独处理。找回现成题解与迁移方法，是两项不同的能力。

## 六、建议的知识组织方式

### 6.1 保留不同对象，通过关系连接

| 对象 | 主要作用 |
| --- | --- |
| 来源与原始快照 | 保留资料身份、版本、内容与授权信息 |
| 原文片段 | 提供可定位的文字、公式、图片与代码依据 |
| API 条目 | 保存精确接口行为和版本信息 |
| 原理与方法 | 保存机制、条件、步骤、限制和反例 |
| 历史案例 | 保存题目背景、已知条件和成功路径 |
| 案例步骤 | 连接输入、操作、输出与后续依赖 |
| 代码与操作示例 | 提供可参考的实现、参数说明与测试情况 |
| 当前题目记录 | 保存自己的证据、假设、计划和实际尝试 |

这些是逻辑对象，落地时可以共用本地数据库和索引。接口应按对象职责组织，而非要求每种对象都部署一个服务。

### 6.2 通用信息统一，专业结构分别保留

统一的信息包括稳定 ID、来源、内容版本、原文位置、派生关系和检查记录。

专业信息分别保存：API 有签名和异常，方法有前提与限制，案例步骤有输入输出，个人尝试有实际执行记录。这样能够共享检索与引用能力，同时保留各自语义。

### 6.3 跨资料关联需要表达关系种类

有价值的关联包括：

- 案例采用某种方法；
- 方法需要某项条件；
- 步骤调用某个 API 或使用某个工具；
- 示例演示某种方法；
- 某观察支持或反驳某个假设；
- 两种方法相似，但成立条件不同；
- 派生说明来自某一版原文。

“提到了同一个工具”适合帮助浏览；“满足必要条件”才与下一步判断直接相关。界面和排序要保留这个区别。

### 6.4 全局知识与单题记录分开

全局知识回答“有哪些方法、它们怎样关联”；单题记录回答“这次实际发生了什么”。

索引可以从原文和整理结果重建。自己的观察、尝试、备注与人工判断要独立备份。资料更新时，历史记录继续指向当时使用的版本，并提示新版本是否出现变化。

## 七、资料处理与质量管理

### 7.1 一条可追查的入库流程

```text
登记来源与文件清单
        ↓
保存原始快照
        ↓
结构解析与完整性检查
        ↓
识别片段角色
        ↓
分别整理 API、方法、案例步骤和示例
        ↓
引用校验、内容检查与必要的人工复核
        ↓
构建检索入口与关联
        ↓
发布可查询的索引版本
```

各阶段保存工具、规则或模型版本。某个环节变化时，可以重做对应产物，而无需丢弃全部整理结果。

### 7.2 清洗先保护技术内容

重点检查代码缩进、公式、字节字面量、转义字符、命令参数、表格和图片说明。格式转换后的正文应保留与原始资料的对应位置。

近似重复资料先分组再处理。两篇内容相似的文章可能对应不同版本、修正或失败条件，值得保留差异。

### 7.3 分别检查“引用真实”和“解释正确”

自动化检查可以验证来源 ID、哈希、引文位置、代码引用和明显数值矛盾。技术审核则检查方法是否成立、前提是否遗漏、原文是否被过度归纳。

对于高频代码，安排独立的功能测试，记录输入、预期输出、依赖和环境。一次测试的结论保留在对应示例上，避免将它扩大为整篇资料都已验证。

### 7.4 新资料进入可搜索范围，精选内容另行提升

建议提供三个质量层次：

- **精选内容**：经过检查的常用方法与示例。
- **普通资料**：保留来源、可以回查的教程与 WP。
- **待整理内容**：新导入或有明显疑点的材料。

新资料可以先通过全文搜索使用；提炼、精排和精选发布逐步完成。搜索时可以显示问题标记，并允许使用者扩大范围查找长尾资料。

## 八、检索与回答的设计建议

### 8.1 先制定查询计划

查询计划包含任务、明确条件、可使用的当前题目记录、目标资料角色、搜索深度和输出形式。

精确符号与常见查询优先用规则处理。存在歧义、跨方向或多步依赖时，再请模型辅助理解。使用者可以修改计划中的假设与筛选条件。

### 8.2 各类内容采用合适的召回方式

| 内容 | 主要入口 | 重要匹配项 |
| --- | --- | --- |
| API | 完整符号、模块、错误信息 | 语言、库、版本、参数 |
| 代码 | 函数名、调用、注释、用途说明 | 输入输出、依赖、完整性 |
| 方法与教程 | 现象描述、概念、目标 | 机制、前提、限制 |
| WP 案例 | 题目特征、中间结果、操作能力 | 当前阶段、依赖和案例差异 |

关键词与向量检索负责互补召回；明确的版本和模式条件分别检查。语义相似用于寻找候选，适用性通过条件与证据再判断。

### 8.3 集中完成排序与来源合并

建议顺序为：

1. 合并多路候选；
2. 将同一原文的摘要、卡片与步骤归入一个来源组；
3. 检查任务需求与明确条件；
4. 必要时对少量候选精排；
5. 结合质量记录和结果多样性选取材料。

避免多个模块在最后反复按标题和词面覆盖覆盖前一轮排序。开发工具中应能查看每条结果由哪一路召回、为什么调整、最终哪些部分进入了模型。

### 8.4 按完整内容选择上下文

给模型的材料优先包含完整的接口条目、方法前提、单个操作步骤或函数。标题、章节、语言、版本和原文位置随内容一起保留。

篇幅不足时，先减少材料数量，或将任务拆小。省略长数据时要保留返回原文的入口，并检查省略内容是否正是本次问题所需的信息。

### 8.5 输出与任务相符

- 查文档：直接展示条目与示例。
- 学原理：解释机制与条件，再连接案例。
- 找代码：展示完整片段、参数与依赖。
- 排错：给检查顺序和结果解释。
- 规划：给候选、依据、条件缺口和下一项动作。

找到相关材料但尚不足以完成判断时，说明具体缺什么。普通用法查询仍可展示带明确示例参数的演示；当前题目的参数另外确认。

## 九、模型、代码与个人工作区怎样配合

### 9.1 模型负责阅读和建议，程序负责稳定记录

模型适合提取查询意图、解释片段、对比案例、提出假设和整理检查项。引用、版本、条件状态、去重和历史记录由程序管理。

4B 与 9B 应在同一组任务上比较质量和等待时间。先确定它们分别适合哪些任务，再决定默认模型与切换方式。

### 9.2 代码需要区分来源与用途

代码可以是原题代码、作者的解题脚本、教程示例、经过检查的通用模板，或为当前问题生成的改写。界面应显示这些区别。

每份示例尽量说明输入、输出、依赖、运行环境、参数含义和验证情况。原始数据与演示参数分开，模型改写也保存与原代码的关系。

对已有代码的语法检查和功能测试分开记录。代码和命令由使用者选择执行；资料包中的样本保持为材料，运行测试安排在隔离环境中。

### 9.3 步骤图跟随实际行动更新

单题工作区保存：观察、假设、子目标、候选、计划、尝试、结果和结论。

模型建议先进入候选区；使用者采纳后成为计划；执行后保存结果。失败记录区分环境受阻、输入问题、实现错误、结果阴性和无结论。

图中连接支持、反驳、依赖和产生等关系。随着输入或环境变化，旧结论可能需要重新检查，系统应保留当时依据和修改历史。

## 十、性能、离线与扩展性要求

### 10.1 快速结果先出现

普通搜索优先返回资料与示例，生成模型随后按需解释。记录首批结果时间与完整回答时间，分别优化。

维护任务、模型生成与查询服务应避免互相阻塞。比赛配置下测试时，同时考虑虚拟机、浏览器和其他工具的资源使用。

### 10.2 维护工作放到后台

解析、提炼、向量计算与索引更新由后台任务完成。查询读取一个完整发布版本，新版本准备完成后再切换。个人尝试记录的变更使用独立版本，避免触发资料重算。

### 10.3 支持新增、修改、改名与删除

来源包有独立身份，文档有稳定身份，内容变化产生新版本。正文位置和相对路径作为定位信息使用。

只更新受影响的片段、向量、示例与提炼记录。删除和撤销导入时，同步处理检索入口及依赖关系；需要保存的历史引用继续指向原快照。

### 10.4 扩展新资料不要求改变整个数据模型

新增一种资料格式，主要增加解析器和角色识别；新增一个技术方向，主要增加术语、方法及评估样本。通用的来源、版本、引用、检索与工作区接口继续复用。

技术选型优先比较低依赖的本地方案。数据量与实测瓶颈再决定是否引入专门的向量或图服务。

### 10.5 离线验收覆盖完整流程

模型、分词器、解析依赖、文档、图片、前端资源和本地登录所需内容提前准备。断开互联网后，从冷启动完成导入、检索、阅读、解释、记录、备份与恢复。

## 十一、用 AES 查询检查设计是否符合需求

### 场景 A：输入“aes 解密”

先给正常解密示例、参数说明和题目分析三个分组。按工作模式进一步区分示例，允许使用者选择语言和库。

示例中的模式与参数明确标为演示条件。使用者尚未提供题目密钥时，仍可查看普通用法；针对当前密文的实际判断则继续收集参数。

### 场景 B：提供模式、密钥和 IV，要求 Python 示例

优先找到对应版本的 API 与完整示例，说明输入编码、填充约定及预期输出。WP 可以作为补充资料，攻击规划不占据主要结果。

### 场景 C：没有密钥，询问下一步路线

先结合源码、接口能力、数据格式和已有观察，检索满足条件的方法与案例。每个候选说明为什么相关，以及需要先验证什么。

### 场景 D：执行后发生异常

读取原始错误与调用方式，优先检索参数、类型、编码、版本和步骤顺序。根据检查结果再决定是否调整方法。

### 场景 E：已完成解密，得到新的文件或数据

更新当前子目标和观察，转向文件格式识别、数据解析或后续案例步骤。上一阶段的加密主题保留在历史中，后续建议跟随新的证据。

这五个场景使用同一批知识，却需要不同检索和输出。它们适合作为最早的一组回归测试。

## 十二、概念验证与验收建议

### 12.1 先验证三项核心假设

| 假设 | 对照方式 | 观察结果 |
| --- | --- | --- |
| 分资料角色处理更有用 | 相同原文、相同模型，比较统一分块与分类型整理 | 可用资料、完整示例和正确条件的命中情况 |
| WP 操作链比摘要更有助于推进 | 比较摘要、步骤列表和带条件依赖的案例记录 | 下一项检查是否具体、是否漏前提、是否引用历史答案 |
| 按任务分流能兼顾质量和速度 | 比较统一深入分析与按需调用 | 误路由、首批结果、总耗时和模型调用量 |

### 12.2 第一批样本怎么选

可以从一个较熟悉的领域选约 20 篇不同写法的 WP、10 份教程及 20 个 API 条目，作为整理方法的试验起点。随后加入另一个领域，检查字段是否过度依赖第一批样本。

WP 应包含步骤清晰、只有最终脚本、依赖图片、跨多个阶段以及缺少关键条件等不同情况。人工先为一部分资料整理参考记录，用于核对自动提炼结果。

### 12.3 按环节评估

| 环节 | 重点问题 |
| --- | --- |
| 解析 | 代码、公式和关键数据是否保留？ |
| 提炼 | 条件、操作和结果是否忠实于原文？ |
| 案例重建 | 输入输出依赖是否成立，缺口是否显露？ |
| 检索 | 前几条结果是否回答当前任务？ |
| 材料选择 | 是否给到完整、足够的证据？ |
| 生成 | 是否正确使用证据，是否混淆假设与事实？ |
| 工作区 | 尝试结果和状态是否能准确保存、修改与恢复？ |
| 性能 | 首批结果、模型读取、生成和维护分别花多久？ |
| 扩展 | 新资料加入后，旧查询与引用是否稳定？ |

### 12.4 特别安排负面测试

- 一篇资料混写几种相近方法；
- 引文真实，但提炼结论夸大；
- 代码完整，却对应另一版本；
- 多份转载挤占前排；
- 原文未说明某条件；
- 短查询存在多个合理意图；
- 工具报错被误判为方法无效；
- 资料改名、删除或重复导入；
- 已有题目记录与新证据冲突；
- 精选库没有答案，但普通资料中有。

比较方案时固定模型、样本和上下文预算，逐次改变一个因素。保留未参与调参的查询，并记录失败例子，才能判断下一步应该调整资料、检索还是模型。

## 十三、建议的建设顺序

### 第一阶段：确认知识结构

完成一批 API、教程和 WP 的人工样本，形成可回查的接口条目、方法说明和案例操作链。检查这些对象是否足以支持真实查询。

### 第二阶段：做好快速检索与阅读

支持精确符号、全文、资料角色分组、完整代码阅读与原文定位。先让使用者能快速找到可操作内容。

### 第三阶段：接入按需模型辅助

验证查询理解、材料解释、案例对比和下一步建议。对照 4B／9B、完整证据单元与普通裁切，确定质量与成本的取舍。

### 第四阶段：接入单题状态与局部关联

让候选建议读取当前证据与尝试记录，保存实际行动；按需要增加条件检查和局部图扩展。

### 第五阶段：验证扩库与持续维护

覆盖不同来源、更多方向、增量更新、版本回查、错误资料和大规模干扰。根据实测结果决定是否训练精排器、增加专门索引或采用更复杂图检索。

每一阶段保留与简单基线的对照。高级算法的价值由具体任务和测试结果决定。

## 十四、研究依据与选型态度

以下研究为设计提供启发，具体算法仍应与本项目样本对照：

- [Adaptive-RAG，NAACL 2024](https://aclanthology.org/2024.naacl-long.389/)：按问题复杂度分配检索成本。本设计进一步将任务目的与搜索深度分开。
- [Sufficient Context，ICLR 2025](https://arxiv.org/abs/2411.06037)：区分材料相关与材料足够，用于检查模型究竟拿到了什么。
- [Contextual Retrieval，Anthropic 2024 工程研究](https://www.anthropic.com/research/contextual-retrieval)：在索引片段中保留所属文档和上下文。可先比较确定性的标题、章节与版本前缀。
- [CodeRAG-Bench，2024 初稿](https://arxiv.org/abs/2406.14497)：分别评估代码相关资料检索与最终程序功能。
- [MiniRAG，ACL 2026](https://aclanthology.org/2026.acl-long.1721/)：将原文块与实体组织成图，作为小模型关联检索的候选路线。
- [RAGStress，2026 年 10 月预印本](https://arxiv.org/abs/2610.04691)：通过资料腐化测试系统，用于设计扩库与错误内容压力测试。

旧项目的审查结果则说明：卡片统一加权、短字符裁切、固定攻击提示输出、查询路径中的维护工作，以及文档身份管理，都需要在重构中分别处理。具体审查记录见本次对话；旧设计材料位于 [本地检索设计目录](D:/user/Desktop/临时/dsh/1/CTF知识库/40_本地检索设计/)。

## 结论

这个知识库应围绕做题需求组织信息：API 提供精确行为，教程提供方法与原理，WP 提供具体案例中的操作依赖。三者通过条件、代码、输入输出和来源互相连接，再服务于查用法、学原理、找示例、排错和路线选择。

WP 的反向整理是其中的重要环节：从公开结果回查前提与步骤，把可复用方法和题目特有数据分开，再与当前证据匹配。缺少的环节保留为检查项，已有的证据保留出处。

重构首先要验证的是：**这些知识能否被准确整理，能否在需要时找到，能否帮助使用者完成下一项有效行动。** 在这三点成立之后，再决定模型和检索算法需要多复杂。
