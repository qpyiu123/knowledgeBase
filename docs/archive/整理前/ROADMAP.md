## 一、这个项目现在是什么

一个本机离线的 CTF 知识库：**1567 篇文档 + 中文模糊检索 + 本地小模型问答 + React 前端**。

它的历史使命已经完成了一轮：
从「一个空的 md 目录」做到了「能一键启动、能检索、能出思路」的可用工具。

现在站在一个岔路口：**功能上它已经够用，但结构上它还没成形。**

## 二、三个判断

### 判断 1：知识库的「量」已经够了，问题在「质」

| | 数量 |
|---|---|
| 手写条目 | 241 |
| 外部导入 | 266 + 1060 |
| **合计** | **1567** |

旧记录称**图谱只有 26 条边、覆盖率 7%**（本批未复现，只能当线索）。

如果这个量级属实，1567 篇文档之间**几乎没有连起来**。检索只能靠词面/语义相似，
而真实 CTF 里最有价值的是「这题和那题是同一类」，这正是图谱该干的事。
但本批不按边数定目标；先由评测判断图谱是否真的提升命中与解题。

> **方向 1：从「堆文档」转向「织网络」。**
> 下一步加知识不该是「再加 1000 篇」，而是「让已有的 241 篇手写条目互相连通」。

### 判断 2：评测体系缺失，是所有改进的瓶颈

现状（2026-10-28 P0 后）：

```
pytest        107 passed  ← 82 原有 + 25 server 离线端点测试
server.py     核心端点有 Mock 覆盖，真实模型/Ollama 未测
webapp        10 passed   ← SSE 契约 + SearchPage 显式参数/错误显示
检索质量      仍无基准    ← 改了排序不知道是变好还是变坏
```

之前做过两轮「模拟 CTF 解题」测试（见 `work/judge/ROUND2_REPORT.md`），
旧记录称 **2/5 解出，17 次检索只有 2 次真正有用（12%）**，**本批未复现**。
那个测试环境不完整、不可复现：Docker 容器要手动起，题目数据每次手搓。

**没有可复现的评测，任何「优化」都是盲改。**

> **方向 2：先建评测，再谈优化。**
> 一小时内能跑完、结果可比的评测集，比任何单点功能都重要。

### 判断 3：模型这条路已经到顶，不该再投入

旧记录的数据（**本批均未复现，不得当结论**）：

```
Qwen3-4B       24 tok/s（结构化判断），883 段/105 秒一次回答
Qwen2.5-7B     13-19 tok/s，且把正确方法判成「不适用」
AirLLM 方案    0.006–0.026 tok/s
显存           4GB（硬件事实），7B Q4 是否为极限未复测
```

可以保留的判断：本机只有 4GB 显存，模型侧继续扩张的边际收益低。
但具体选 4B 还是 7B、是否再投入模型侧，应由后续可复现评测决定，
而不是沿用未复现的旧数字。

> **方向 3：停止在模型侧投入，把算力用在「工具出事实」上。**
> 项目已有的架构原则是对的：**工具产生事实，模型只做判断/排序**。
> 沿着这条路走，而不是指望模型变聪明。

## 三、建议的主线：让知识库「会推理」，而不是「会检索」

现在的链路：

```
查询 → 检索 → 列出文档 → 模型选一条回答
```

目标链路：

```
查询/附件 → 侦察 → 检索 → 图谱关联 → 结构化证据 → 模型判断 → 可执行步骤
```

差别在于：**中间多了「图谱关联」和「结构化证据」**。

具体到写什么，按我的优先级：

### P0 —— 打地基（不做后面都是空谈）

| # | 事项 | 状态 |
|---|---|---|
| 1 | `git init` + 基线提交 | ✅ 已完成（`b9ebe89`） |
| 2 | 修 `setImmediate` + stale closure + SSE 契约 | ✅ 已完成（含前端测试） |
| 3 | `server.py` 离线 Mock 测试 | ✅ 已完成（25 个） |
| 4 | 建 20 条评测集 | ⏳ 未做，转入 P1 |

**第 4 条是下一阶段重点。** 评测集建议这样建：

```yaml
# tests/eval/queries.yaml
- q: "题目给了同一个 n，e1=3 e2=65537，两组密文"
  expect_top1: crypto/rsa-common-modulus-attack.md
  expect_in_top5: [crypto/rsa-common-modulus-attack.md, crypto/rsa-wiener-attack.md]
  kind: 手写条目（必须命中）
- q: "Solidity calldata tuple head overflow"
  expect_top1: _des/cards/...(那篇 0CTF 卡)
  kind: 导入条目（宽松，进前 5 即可）
```

跑法：`kb bench-retrieval`，输出 **top1 命中率 / top5 命中率 / MRR**。
以后每次改排序，先跑这个。

### P1 —— 让图谱真正起作用

这是当前最大的结构缺口，也是最能体现「知识库」而不是「文档集合」的地方。
2026-10-28 验证：**1567 节点 / 26 边 / 8 条跨方向 / 17 篇源文档**。
但边数不是目标，是否有用由 P1 评测判断。

| # | 事项 | 做法 |
|---|---|---|
| 5 | 给 241 篇手写条目补关系 | 先补 50 篇高频条目的 `requires` / `differs_from` |
| 6 | 实现「反向索引」式关系建议 | 从已有 26 条边出发，找出「很像但没连」的文档对，人工确认后加边 |
| 7 | 检索时按关系加权 | 现在图谱结果只排尾部；应让 `requires`/`illustrated_by` 真正提升排名 |

**第 6 条是杠杆点**：与其让模型去猜关系，不如让工具**找出候选对**，
人只做「是/否」。这个模式在 `hint` 里已经验证过有效
（工具出事实，模型只判断）。

## 六、如果只做三件事

时间有限的话，按这个顺序：

1. **建可复现评测集** —— 先有尺子，再谈检索/图谱/模型改动。
2. **检索可解释** —— 命中段落、命中原因、类型筛选、相似结果整理。
3. **反馈与评测闭环** —— 记录有用/无用，按真实记录迭代。

图谱与内容补齐放在评测之后，不按边数或篇数凑指标。
