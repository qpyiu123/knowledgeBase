# 界面、用户控制与语言文档计划

2026-11-05 · R6 规划。开发和记录继续放在移动硬盘项目。R5.2 的真题整理与资料缺项继续保留；本轮先把新增需求和验收方式写清楚。

## 1. 要做成什么样

- 打开应用就能查资料，生成模型不随应用启动。用统一的“设置”管理本应用的各项配置和模型运行状态。
- 主界面继续服务于搜索。现有解释入口改为“深度搜索”，只新增“直接模式”和“翻译”。这三项的最终结果放在侧栏，运行中不占用搜索结果区。
- 在现有导航中增加“语言文档”。输入语言名和函数名，直接看到中文解释、准确签名、用法和来源。
- 用实际题目和查询比较两套本地向量编码器。选定后，项目日常使用和分发只保留一套编码器及对应索引。

界面复用现有 React / Mantine 布局、控件、明暗主题和阅读交互，按 [开发规范](开发规范.md) 写中文提示。此次新增设置页与结果侧栏，其他页面不重做视觉样式。

## 2. 统一设置与按需启动

### 已有实现

当前双击 `启动.cmd` 走 `-NoModel`，可查资料，但要使用解释需停掉查询服务再按另一组参数启动。应用的配置散在 `config.toml`、启动参数、环境变量和浏览器状态中；主界面还显示模型连接状态。旧版有专门的设置页和模型管理区，可参考其保存配置、启动、停止及区分当前状态的做法。

### 使用流程

1. 双击入口只启动网页和资料服务。打开首页、打开设置、关键词查询与查语言文档都不加载生成模型。语义编码器也只在请求语义补充或明确重建其索引时使用。
2. 建议默认采用**首次使用时加载**：第一次选择深度搜索、直接模式或翻译时，才启动所选生成模型。设置中可切为“仅手动启动”，也可关闭这三项功能。显式 `-NoModel` 继续作为强制仅查询方式。
3. 设置可主动启动、停止、重启和查看状态。停止生成模型后能继续搜索。4B 与 9B 只运行当前选择的一份；切换时先释放旧实例。空闲释放的默认时长用比赛机实测后再定。
4. 加载失败时，主界面保留搜索结果；给出“此功能未就绪，去设置检查”等短提示。缺权重、端口占用、设备失败和启动日志放在设置页。关闭应用时清理本项目启动的进程，不停止其他应用的服务。

### 设置放在哪里

| 分组 | 可配置内容 |
| --- | --- |
| 外观与使用 | 明暗主题、默认搜索方式、结果数量、默认翻译方向等界面偏好 |
| 搜索与索引 | 是否默认补充语义结果、关联提示选项；查看资料与索引状态、手动更新索引 |
| 模型 | 按需/手动/关闭，4B 或 9B、Vulkan 或 CPU、设备、线程、上下文和输出长度；查看运行状态，启动、停止、重启 |
| 资料与工作区 | 应用已经支持的资料、附件、题目记录位置与附件限制；显示修改后的实际路径 |
| 高级 | Python 解释器、监听端口、搜索分块与运行参数等现有用户配置；明确哪些值需要重启或更新索引 |

第一步列清现有用户配置和读取位置，逐项归组。常用项直接可改，技术项折叠在高级分组；不让用户为同一选项同时改页面和配置文件。运行统计、构建产物和内部算法常量不作为可编辑项。

推荐沿用项目默认配置，个人设置保存在现有本机工作区范围内。网页、命令行和启动器读取同一套有效值；显式启动参数或环境变量覆盖当前运行时，页面标出覆盖来源。“保存”和“重启应用”分开：能即时生效的直接应用，模型加载参数注明下次启动生效，影响索引的参数等用户更新索引后才使用新版本。查看设置、保存设置和健康检查都不触发预加载。

实现时先核对 `tools/llama_runtime.py`、`tools/kb/config.py` 和启动脚本的调用方。复用已有启动和取消逻辑，限制为一个生成实例，避免并发请求重复加载。现有 CLI 参数和诊断脚本需要兼容或同步更新；常规启动不再用“启动查询”隐式加载生成模型。完成后从设置页就能开关和切换，无需重启查询服务来切换解释。

## 3. 主界面与结果侧栏

| 操作 | 处理什么 | 结果 |
| --- | --- | --- |
| 普通搜索 | 关键词、可选语义补充和已有条件关联 | 资料继续显示在主结果区 |
| 深度搜索 | 继续使用命中小节、参考代码和用户选择的题目记录 | 任务成功后在右侧栏显示最终结果、资料出处与代码 |
| 直接模式 | 将本次输入原文作为唯一用户消息发送；不追加系统提示词、题目记录、知识库片段或历史消息，也不先检索 | 任务成功后在右侧栏显示最终文本 |
| 翻译 | 仅发送要翻译的文本、选定语言和必要的翻译要求；保留函数名、代码块、参数和报错 | 任务成功后在右侧栏显示译文，原输入保留 |

直接模式仍使用运行时所需的消息格式，但项目不会向消息内容加任何提示词。翻译可以有明确的目标语言，默认方向作为设置项，用户在任务中也可选。除此之外不增加编程、对话历史或新的生成模式。

- 主界面操作名用“深度搜索”“直接模式”“翻译”，深度搜索进行中显示“正在搜索…”，直接与翻译显示“正在处理…”“正在翻译…”。移除首页的模型名、连接徽章、“问模型”和“正在思考”等文案；设置页保留准确的模型名称与状态。
- 复用现有侧栏组件和阅读样式，右侧提供结果区。运行中主界面只显示任务状态与取消操作，侧栏在完成时才接收最终回答，不显示中间过程、思考字段或半截文本。
- 搜索输入、列表、滚动位置和筛选不被侧栏替换。新搜索可以继续；取消、失败或已过期的请求不得覆盖当前结果。切到另一题时，旧题的任务完成也不抢占当前界面。窄窗口仍能关掉侧栏继续看搜索。
- 第一版复用当前流式协议和请求编号。前端可暂存最终文本片段，收到成功结束事件后统一显示；后端不转发内部思考字段。错误与取消按原有方式结束。

验收覆盖按钮、占位符、无结果提示、加载状态、无障碍名称和错误提示。用模型替身检查直接模式请求体只有一条原样用户消息；翻译不会搜索题库；完成前不渲染回答，完成后结果只出现在侧栏。

## 4. 比较两套向量编码器

### 可直接使用的资源

| 候选 | 本机现有文件 | 实际使用规格 |
| --- | --- | --- |
| 新版 BGE-small-zh-v1.5 | E 盘 `models/bge-small-zh-v1.5-onnx/model_quantized.onnx`，约 24.0 MB | 当前 ONNX CPU 路线，现用索引 512 维。[BAAI 模型说明](https://huggingface.co/BAAI/bge-small-zh-v1.5) |
| 旧版 Qwen3-Embedding-0.6B | 旧库 `80_知识工作台/models/Qwen3-Embedding-0.6B-Q8_0.gguf`，约 639.2 MB | 沿用旧版 llama.cpp 编码与归一化，旧代码使用 1024 维。[Qwen 模型说明](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B) |

大小为权重文件字节数换算，不是运行内存。比较只涉及检索编码器；用于解释的 Qwen3.5 4B / 9B 保持原方案。两候选已有本地文件，不重下权重。

### 怎么测

1. 冻结一份当前语料、切分和查询预期。各用自己的查询格式、分词和池化方式；保持候选数、关键词排名和融合规则一致。为两套编码器各建临时向量索引，关键词索引共用，不改现用索引。不拿旧版全库分数直接和新版比。
2. 用现有 22 条、60 条检索集和 R1 速查集做回归。另选已复核的真题线索、口语描述、中英混输、函数与报错、同名函数和无合适资料的查询。精确查函数单独报告，重点看语义补充比关键词多找到了什么。
3. 对同一问题记录前五是否有用、首个有用结果位置、无关推荐和关键前提遗漏。逐条保存两者分歧，避免只用一个平均分决定。
4. 先在同一机器跑 CPU 对照，记录线程和运行方式；再用拟部署配置在 8845HS / 24GB 比赛机核对。记录冷加载、热查询、语义结果出现时间、整库构建时间、峰值内存、索引和权重体积。再看同时使用 Vulkan 解释时，语义查询是否明显拖慢。重复查询有足够样本才汇总中位数与第 95 百分位。

### 怎么选

先过已有精确查询与关键题型回归。语义候选要在实际卡点或模糊查询上找到更多可用资料，再考虑切换。命中质量相近时选等待更短、内存与磁盘占用更低的一套；若较重的候选能解决明显缺口，报告代价并在比赛机确认可接受后采用。没有实测前保留现用 BGE。

确定后，只有胜者进入应用配置、索引与后续发行清单。用所选模型重建并验证独立的向量索引，完成后切换，关键词索引保持可查；模型、维度、分块或查询编码规则变化时不混用缓存。确认没有运行依赖后，清理临时对照索引和项目内不再使用的编码权重；例如若保留 ONNX 量化版，就不再携带同一编码器的全精度和 GGUF 副本。旧仓库原件保留。

## 5. 语言文档：融入现有卡片

### 先用已经下载的

旧库 `65_语言文档/2026-10-23` 与 `2026-10-24` 的清单共有 11 + 88 条。包含 Python、PHP、JavaScript、Node.js、Java、Go 和常用库。清单中有官方中文正文，也有中文选段说明，入库时按每条的来源、版本和许可核对，不能统一标成官方中文全文。旧库的 Node.js 资料已有 Buffer 与 zlib。两个批次的同源内容先合并。

新版 R1 已通过现有接收流程导入 Python 3.9 的 base64、json、re 官方中文正文，保留版本、来源、许可和函数小节；也已有 Python 解码排错卡。参见 [R1 实施记录](../records/R1-实施记录.md)、[方法卡协议](专题/方法卡协议.md) 和 [资料清洗任务书](专题/弱模型资料清洗.md)。沿用其原文核对、证据保留和反例检查做法。

| 批次建议 | 先整理什么 |
| --- | --- |
| 首批 | Python、PHP、JavaScript / Node.js：字节与编码、正则、替换、缓冲区。先选已有来源且当前题解常用的函数。 |
| 补缺 | C / C++：常见字符串、内存、输入输出函数及版本差异。这两批旧归档未列出专门的 C/C++ 手册，实施时再查其他旧资料；缺项取目标环境的官方手册或标准对应条目。 |
| 后续 | Java、Go 和常用库优先复用旧库，其他语言或方言按实际查询缺口补。 |

已有页不再下载。缺页按目标版本接收必要章节，记录原文页、函数锚点、版本和许可，再整理中文说明。JavaScript 语言行为以 [ECMAScript 规范](https://tc39.es/ecma262/)为核对来源，Node 专用接口查 [Node.js 官方文档](https://nodejs.org/api/buffer.html)；历史 MDN 页面仍可作阅读参考。只收符合许可的内容，中文整理与官方原文分别标注。

### 怎么组织

- “语言文档”是界面分区与检索筛选，沿用同一套 Markdown 卡片、索引和阅读器。保持 Web、Crypto、Reverse 等题型分类；不为每种语言新建数据目录、不把整套 HTML 站点加入索引。
- 优先在已有速查卡、方法卡或引用文档中补齐准确的函数小节。通用解释只保留一个主出处，同一模块相关函数合在一张卡里；相关 CTF 卡用锚点引用，并保留本题用法、前提与反例。确无合适卡片时按现有结构补一张模块卡，不按每页手册铺目录或堆重复卡。
- 沿用已有 `kind: api` 和标题、标签、来源、版本字段。现有结果类型主要靠目录推断；本期让可查的小节或卡片带语言和完整符号，并按资料类型筛选，不用目录名或题型充当语言分区。一个函数小节可在语言分区出现，原方法卡仍按原方向查询。
- 函数小节保存：**语言或运行时、模块和完整函数名、签名、中文说明、参数和返回值、报错或版本限制、最小示例、原文位置**。正式示例与 CTF 场景分清。外文译写时不改标识符、代码和边界条件。

### 怎么验收

- 先做少量样例，固定“语言 + 完整函数名”“函数名带参数”“中文用途”“同名函数”“报错原文”几组问题。示例：`Python base64.b64decode`、`PHP str_replace`、`Node.js Buffer.from`。查询对应已收录符号时，语言分区首条进入正确函数小节，并直接显示中文解释及版本。
- 重名符号按语言、库和版本区分；未收录时提示可用相近条目或缺项，不让生成模型补写不存在的手册答案。
- 关闭生成和语义补充也能查到已收录精确函数；原方法卡、代码及条件检索保持可用。记录来源复核、许可、重复合并和固定查询结果。扩下一批前先查首批误命中与缺项。

## 6. 实施顺序

| 批次 | 先做什么 | 完成条件 |
| --- | --- | --- |
| R6.1 | 统一设置、保存与状态；启动时不加载生成模型 | 启动、设置和搜索无预加载；手动、按需、停止、切换和配置生效范围可验证。 |
| R6.2 | 主界面文案、右侧结果、直接模式和翻译 | 主搜索不被替换；只显示完成结果；请求内容、取消和回退通过测试。 |
| R6.3 | 在同一批资料和固定问题上比较编码器 | 有质量、等待时间、内存与体积结果；比赛机确认后只保留合适的一套。 |
| R6.4 | 语言文档分区和首批函数卡，之后按缺口扩充 | 函数直接命中中文小节；已有卡片、来源和索引回归通过。 |

语言资料可先盘点和做少量样例；编码器对照开始后固定同一批正文，新增资料另跑回归。每批更新[当前进度](当前进度.md)、对应验收记录与版本索引，再提交本地 Git。发布目录继续按需生成。

**实施前请确认一项默认行为：** 建议应用启动后不加载，第一次使用深度搜索、直接模式或翻译时自动加载；设置中可以选“仅手动启动”。若你希望默认也必须手动启动，就以手动为默认。
