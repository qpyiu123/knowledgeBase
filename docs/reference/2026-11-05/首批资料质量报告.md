## 二、入选标准

### 硬要求

1. 原始 Markdown 在本地，字节哈希与旧下载清单相符。
2. 能确认来源项目、修订、作者或项目署名，保存本地许可证据。
3. 关键结论能回查文字、代码或已归档图像；不是只有题名或最终 flag。
4. 能明确写出输入条件、操作与输出之间的关系。
5. 原文缺失内容保留为缺口，整理者的检查建议另作标记。

### 取舍

- 不按长度、标签数或来源名气自动打高分。
- 一篇文章中的有用片段可入选，其他部分保留问题标记。
- 本地缺图时，区分图只是辅助说明，还是结论的唯一依据。
- 保留失败转折、后续更正、版本限制与相反条件，不压成成功故事。
- 纯速记、未定义变量较多或默认偏移容易被照搬的材料先暂缓。

## 四、清洗与归档规则

### 原始层

复制九个来源的原始字节，使用原有资料 ID；保留旧路径、旧库身份、来源 URL、修订号和哈希。模型权重、个人题目记录和旧索引保持原样。

三个 Hackergame WP 的旧条目把许可写作 NOASSERTION；本次读到了旧库已下载的仓库 LICENSE，题解许可明确为 CC BY-NC-SA 4.0。原来的元数据值与新的许可证据同时保留。

### 清洗层

规则 preserve-markdown-v1：

- UTF-8 解码，单独处理 BOM；换行统一成 LF。
- 删除文件开头的站点 front matter 与正文之外的 Vue script setup 导入。
- 代码围栏内出现相同标签时原样保留。
- 不翻译繁体，不改代码、空格缩进、公式、转义、表格、偏移和字节字面量。
- 保留 clean 行号到原始行号的映射，逐条登记删除原因。

原文中的历史地址、会话样例、安装命令和不安全的读取方式仍属于历史资料，既不执行，也不当成当前环境参数。默认检索只使用选定知识与依据，整篇原文通过来源入口查看。

### 知识层

发布十七条结构化记录、五十九处逐字引文：

- 总结与成立条件分别保存。
- 边界注明是作者明确陈述、代码读取还是整理者推得的迁移边界。
- 步骤保存输入、操作、输出、依赖及结果性质。
- 案例常量与迁移时要重新确定的变量分开。
- unknowns 保留资料缺项，next_check 明确标为整理者提议。
- 作者给出的输出与本机复现结果分开；本批没有执行赛题。

## 五、测试库与评价

SQLite 中的来源、知识、证据、代码和附件分表，原始 ID 与修订沿用。FTS5 只索引精选知识和引文；原文的其他小节保留阅读入口，不进入精选排序。

二十二条评价问题覆盖查找、条件不足、资料缺项、历史输出与实际复现的区别。问题、相关条目、预期要点和禁止擅自补充的条件独立保存在 evaluation.json。

这些是整理者编写的评价草稿。全部来源参与过本批整理，review 分组也不算严格盲测；需要人工核对标签后再比较检索或生成方案。当前未计算召回率、解题率或模型耗时。
