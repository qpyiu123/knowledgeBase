## 4. 不调用生成模型时，应当怎样得到好结果

### 4.1 先保住完整资料，再整理速查内容

建议保留两种阅读入口：

- **精选速查**：短而完整的 API 用法、技巧、条件检查、关键决策和参考代码。沿用当前测试库的来源与依据要求。
- **全库原文**：完整 WP、教程、官方文档、源码、图片和题目附件。尚未精读的材料仍可搜索，标清整理状态；精选条目能直接跳回对应原文位置。

不必把整篇语言文档和每一段 WP 都蒸馏成新卡片。完整原文保留细节，精选记录帮助快速选到有用位置。同源副本合并展示，避免一篇长文及其多个导入版本挤满结果。

质量状态和资料类型分别记录。官方文档、WP、教程、方法卡、脚本说明各自适合不同问题，不能统一按“方法卡优先”排序。

代码需要保留输入格式、依赖、运行环境、输出含义和原题常量。新脚本的自检通过记录与完整赛题求解记录分别展示。例如现有 Coppersmith 脚本的求解入口有小范围枚举限制，Solana 地址派生包含演示内容，查询结果应写清实际功能。

### 4.2 查询语言与库文档，要优先命中函数和具体行为

旧版已有官方文档提取与搜索代码，以及本地归档页面，可以直接复用资料。先查函数、模块、参数、异常文本和语言版本，再补 CTF 中常见用法或误区。

应保留完整标识符、原始错误字符串和关键符号，避免只靠中文主题词。别名表从少量确定关系开始，例如 Z3Py 与 Z3 的 Python 接口；相关但行为不同的函数保留区别。

搜索结果直接提供：**函数或小节名、命中正文、原始代码、版本/依赖、来源位置**。查正常 API 用法时优先给正常用法，随后列相关技巧，不自动展开整套攻击步骤。

### 4.3 解题灵感先由“条件 + 案例关联”提供

当前测试库已经记录机制、条件、限制、案例变量、步骤和信息缺口；接续版也有 signals、关系字段及关联阅读实现。先把这些内容用于直接展示：

1. 从原查询、附件静态信息和用户记录中提取已出现的特征，保留原查询用于检索。
2. 找到同类机制、相近卡点和参考案例。
3. 每个候选显示“为什么相关、还要确认什么、下一步查什么”，附原文依据。
4. 主结果优先直接相关资料，跨方向类比放在关联阅读中，不挤掉精确 API 和代码命中。

例如输入“RSA 知道部分素数”，结果应先指出还需确认高位/低位、未知位数和其他已知量，再列相应方法和参考代码。输入里没有给出的条件保留为待查。

这种联想可用已有字段、检索和少量关系规则完成，日常查询无需先让生成模型改写问题。向量编码器仍可用于语义检索，它与生成长回答的工作量不同；精确命中不应等待编码器加载。

| --- | --- |

## 5. 建议的结构：一个应用，几个可单独比较的小模块

```text
旧原文 / 官方文档 / 代码 / 附件       精选条目 / 方法卡
                 \                   /
                  比赛前构建索引
                         |
用户查询 --> 符号与关键词检索 --> 立即显示资料、代码和来源
             |           |
             |           +--> 条件检查与相关案例 --> 有依据的联想
             +--> 可选语义检索 -----------------> 补充候选

当前题目记录 --> 提供已知条件、待查项和尝试结果
用户点“解释” --> 选取命中小节与代码 --> 旧 Vulkan 模型服务
```

沿用接续版现有网页组件，不新增一套视觉风格。数据、检索、关联提示、题目记录与模型解释保持清楚的接口，独立比较效果后再决定组合方式。

### 适合先试的三个子系统

| 试验 | 用已有内容怎样做 | 观察什么 |
| --- | --- | --- |
| A：文档与代码快查 | 同时查官方文档、正文和代码；按命中小节展示，提供来源跳转 | 不开生成模型，能否直接找到可用 API、片段或参考代码；先显示结果要等多久 |
| B：条件驱动的关联提示 | 用精选记录和验收过的方法卡，展示已知条件、缺项、关键区别、相关案例 | 模糊描述能否找到正确方向；是否错误补全了题目条件；增加了多少无关建议 |
| C：卡点与尝试记录检索 | 将“观察 → 判断变化 → 下一步检查”作为案例中的局部记录，结合用户当前问题查询 | 比按整题相似度寻找 WP，能否更快找到有用的下一步 |

先做 A，再比较 A+B；C 在题目记录结构整理后试验。现有图谱只有 1856 个节点、26 条关系，优先补有实际查询用途的关系，不以边数作为阶段目标。暂缓多代理推理、多轮模型规划、全量重蒸馏和额外常驻检索服务。

## 6. 模型、内存和题目记录怎样处理

### 保留比赛机已验证的模型方案

旧版记录了 Qwen3.5 4B / 9B Q4_K_M、Qwen3-Embedding-0.6B，以及独立 llama.cpp CPU / Vulkan 进程。聊天与编码服务端口分别为 8811、8812。用户已补充确认核显推理在比赛机可用，此次沿用该结论。

生成模型按需加载，搜索可以在生成模型关闭时使用。4B / 9B 切换沿用旧版设置；24GB 内存还要供系统、核显共享内存和比赛工具使用，不默认同时常驻两个生成模型。

接续版现有 BGE 向量索引不能直接给旧 Qwen 编码器查询。恢复旧编码器路线时，应使用与该编码器匹配的索引；已有原文和其他关键词索引继续复用。编码器的调整放在精确查询可用之后，避免同时改变模型、数据和检索方式后难以比较。

### 题目记录服务于当前卡点

接续版已有 fact、attempt、reference 记录，值得保留。可补充当前目标、待确认条件和假设；已知事实来自题面、附件检查或用户确认。

现有模型材料收集全部事实和最前面的十条失败尝试，再按长度截断。后续应选择当前阶段相关、较新的记录，并区分“程序没有运行成功”和“检查结果排除了方法前提”。这也会改善不用生成模型的关联提示。

附件当前默认上限为 8MB，真实二进制和流量文件可能超过它。可考虑读取用户指定的原文件路径、按需检查文件头和局部内容，减少反复复制；仍保持静态查看，不自动执行题目附件。

## 7. 下一轮按什么顺序推进

1. **保护和恢复现有成果**：保存 41 套新卡及脚本，补备份范围，恢复 E 盘环境；不移动或重下旧模型。
2. **让新增资料可查**：修复三张卡及验收器，复核脚本功能范围，更新索引、任务表和项目记忆。
3. **跑通不用生成模型的快查样例**：用现有 17 条精选知识、一小批验收方法卡和旧官方文档，接通搜索、命中小节、原始代码与来源阅读。
4. **补资料完整性**：按常用查询优先接回旧原文中的代码、图片和依赖，不对 1911 份文档同时重新摘要。
5. **比较关联提示**：围绕语言用法、条件模糊、相近题型、失败排错，测试 A 与 A+B；根据误报调整规则和资料。
6. **接回旧模型解释**：统一网页与命令行接口，使用用户验证过的 Vulkan 运行方式；解释按需触发。
7. 再扩充资料与探索 C，不把未验收批次继续叠到索引外。

资料构建安排在比赛前。旧版部分查询入口会检查证据索引并在变化时触发构建，整合时应将重建移到维护命令，查询只读已发布的索引。

空间方面，原始资料和模型保留一份主副本，通过配置定位；索引单独管理。旧发布解压副本此前已清掉约 10.69GB 的精确重复文件，剩余差异文件包含不同的状态库，需要保留。精选测试库约 1.9MB，原文、映射、笔记和数据库各有用途，继续保留。详见[空间清理记录](D:/user/Desktop/临时/dsh/1/ctf知识库-重构/docs/项目空间清理记录.md)。

## 8. 怎样判断这次真的更适合比赛

### 已有速度记录怎样参考

| 记录 | 条件与结果 | 可用于定位的问题 |
| --- | --- | --- |
| 旧版短查询 | 开发机 CPU、6 线程、8192 上下文；检索约 0.563 秒，4B 查询合计 15.307 秒 | 生成回答占了主要等待时间 |
